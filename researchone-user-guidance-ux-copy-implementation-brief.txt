IMPORTANT OPERATING INSTRUCTION

Treat this as a product-correctness task, not a marketing polish task. The redesign made ResearchOne an all-purpose deep-research system that can perform descriptive information gathering, explanation, comparison, synthesis, discovery, implementation research, quantitative analysis, and claim/story verification. The current interface still teaches portions of the former universal-hypothesis/falsification workflow. That mismatch can cause the planner, user, and report expectations to drift back toward the exact failure the redesign was intended to correct.

Do not rewrite copy in isolation from actual behavior. Before changing a capability statement, trace the relevant frontend component, API response, entitlement rule, and worker behavior. If the UI promises a behavior that the code does not perform, either implement the behavior in the same workstream or narrow the copy to the behavior that exists. Never make unsupported absolute claims.

2. PRODUCT LANGUAGE MODEL TO USE EVERYWHERE
======================================================================

Adopt the following user-facing mental model.

ResearchOne helps a user answer a research question by:

1. understanding the requested outcome;
2. proposing a research plan;
3. gathering and reading relevant sources;
4. selecting specialist analysis appropriate to the request;
5. checking important claims and limitations;
6. producing a cited report that distinguishes evidence, interpretation, uncertainty, and contradiction.

The analysis is adaptive. A descriptive request should not be turned into a hypothesis. A verification request should receive explicit claim decomposition, corroboration, counterevidence, and a verdict standard. A quantitative request should use quantitative specialists when sufficient data exists. A comparison should use stable criteria. A discovery request should distinguish observed gaps from speculative opportunities.

Canonical user-facing request families:

- Learn or explain: “Explain how municipal bond insurance works and summarize the current market.”
- Compare or choose: “Compare these three products for a small medical practice.”
- Verify a claim or story: “Check whether the claims in this article are supported.”
- Synthesize a field: “Map the major approaches to long-duration energy storage.”
- Find opportunities or gaps: “Identify underserved problems in residential heat-pump installation.”
- Plan or implement: “Create an evidence-based implementation plan for SOC 2 readiness.”
- Analyze numbers: “Extract the reported metrics and compare performance across these studies.”

These are examples, not new hard-coded mode names. The user can describe an outcome naturally; EZ mode should route it.

Canonical terms:

- “EZ Research”: guided research in plain language; ResearchOne chooses the approach.
- “Research Lab”: advanced controls for experienced users who want to influence methods, specialists, sources, models, formats, or verification intensity.
- “Research plan”: the proposed question, scope, deliverables, sources, approach, assumptions, exclusions, expected time, and expected charge.
- “Requirements”: user-supplied constraints that must be followed.
- “Assumptions”: system-proposed interpretations caused by ambiguity; the user can correct them.
- “Dossier”: one research project containing the request, confirmed plan, run history, report, sources, revisions, and related spinoffs.
- “Revision”: update a section of the current report; it does not automatically repeat the entire research process.
- “Spinoff”: start a new full research run using a prior report as context.
- “Corpus”: the user’s reusable source collection.
- “Ingest”: add material to the reusable corpus.
- “Attachments”: sources or context used for one research request unless the UI explicitly offers to save them to the corpus.
- “Living Report”: monitoring that checks a finalized report for relevant new information during a defined active period.
- “Reverse-Citation Watch”: monitoring for later works that cite sources or works associated with a report, if that is the implemented behavior.

Internal terms to hide from EZ-mode default views:

- classifier confidence;
- competence check;
- refinement rounds;
- orchestration profile;
- connector class;
- pipeline B;
- agent enum or agent IDs;
- V1/V2;
- backend stage names;
- model slug;
- source-corroboration enum IDs.

Plain-language replacements:

- “Detected intent” -> “What ResearchOne thinks you need”
- “Classifier confidence” -> “How sure we are” only when useful; otherwise omit
- “Orchestration profile” -> “Saved research setup”
- “Supplemental URL” -> “Web pages to read”
- “Supplemental context” -> “Extra instructions or background”
- “Filter tags” -> “Limit research to these source tags”
- “Pipeline trace” -> “Research progress”; offer “Technical trace” separately
- “Ingestion consent” -> “Help improve shared research intelligence”
- “Falsification criteria” -> use “Verification standard” for story/claim verification or “Test criteria” for hypothesis testing; do not render for unrelated intents

3.1 PUBLIC HOME, METHODOLOGY, FAQ, COMPARE, PERSONAS, AND PRICING

Replace fixed-pipeline positioning with adaptive-method positioning.

Recommended hero direction:

Heading:
“Deep research that adapts to the question.”

Supporting copy:
“Ask for an explanation, comparison, evidence review, opportunity map, implementation plan, or claim verification. ResearchOne builds a plan, gathers sources, selects the right specialists, and produces a cited report with uncertainty and contradictions made visible.”

Do not promise:

- exactly ten stages on every run;
- exactly seven agents on every run;
- a Skeptic on every claim;
- quantitative extraction on every run;
- a fixed pipeline shape;
- a result that “proves” truth;
- universal falsification criteria;
- static operational status, uptime, or SLA facts unless dynamically backed and contractually true.

Methodology should explain both shared safeguards and adaptive methods.

Shared safeguards can include:

- source attribution;
- claim-to-source binding where supported;
- separation of evidence from interpretation;
- uncertainty and contradiction handling;
- source-quality/context checks;
- traceability of plan and run;
- verification appropriate to the requested outcome.

Adaptive examples:

- descriptive research: coverage, organization, currency, and source diversity;
- comparison: consistent criteria and comparable evidence;
- story verification: claim decomposition, corroboration, counterevidence, and verdict rules;
- quantitative research: extraction, unit normalization, calculations, and data-quality checks;
- discovery: observed needs, existing attempts, constraints, and uncertainty;
- implementation: requirements, dependencies, risks, and ordered actions.

FAQ must answer:

- What kinds of questions can I ask?
- When should I use EZ Research versus Research Lab?
- What is Standard versus Deep?
- How does ResearchOne choose specialists?
- Does it always try to prove or disprove something? Answer: no.
- Can it verify a news story, document, or claim?
- What happens when sources disagree?
- What does a citation mean, and what does it not guarantee?
- Will it read a link merely pasted in the question? Reflect actual behavior precisely.
- What is the difference between attachments and the Corpus?
- What is stored, shared, or private?
- What does a report cost and when am I charged?
- What is a Dossier?
- What is a Living Report?
- What does BYOK change?
- What happens if a run fails?

Pricing:

- Replace compressed dash-separated feature strings with scannable feature rows.
- Explain Standard and Deep beside the first occurrence.
- Verify all quotas and eligibility against code.
- Replace “all five modes” if the redesigned request families are adaptive rather than five fixed modes.
- Explain wallet credits versus subscription quotas.
- Explain BYOK subscription cost versus charges billed by the model provider.
- State whether BYOK runs are actually unlimited, rate-limited, or subject to fair use and non-model platform costs.
- Correct add-on eligibility contradictions.
- Make “Coming soon” unmistakable and prevent checkout paths for unavailable features.

3.4 PLAN REVIEW AND CONFIRMATION

EZ-mode plan review should show, in this order:

1. What you asked for
2. What the report will deliver
3. Scope: timeframe, geography, audience, and included subjects
4. Sources to read or seek
5. How ResearchOne will approach it
6. Your requirements
7. Assumptions to confirm
8. What is not included
9. Expected depth/time
10. Expected quota or wallet charge

Required semantic correction:

Do not merge user requirements/constraints into assumptions. Requirements are authoritative user instructions. Assumptions are system interpretations and must be separately editable.

Replace generic exclusions such as “anything not listed is out of scope” with concrete exclusions, coverage limitations, unavailable sources, and unresolved ambiguities.

- collapse the internal agent roster under “Technical details”;
- summarize it as “How we’ll approach it”;
- do not show classifier confidence by default;
- do not show competence checks, refinement-round counts, enum IDs, or connector classes;
- show specialist roles as planned capabilities, not guarantees that a named agent has already executed.

In Research Lab:

- retain detailed routing and agent information;
- provide a glossary for each control;
- clearly distinguish “planned,” “running,” “completed,” “skipped,” and “failed.”

Confirmation:

Replace bare “Confirm & run” with contextual copy such as:
“Confirm and start research”
Helper: “This starts source retrieval and analysis and uses [quota/estimated wallet amount].”

Auto-confirm:

- explain the behavior before it is enabled;
- provide a conspicuous pause/cancel control;
- do not auto-confirm low-confidence plans, materially changed plans, plans with unresolved safety/legal issues, or plans whose cost exceeds the user’s configured threshold;

“Research [topic/question] for [audience/purpose]. Cover [scope/time/place]. Use or prioritize [required sources]. Compare or verify [important points]. Deliver [format].”

Verification template:
“Evaluate the important factual claims in [story/document]. Separate confirmed, contradicted, unsupported, and unresolved claims. Use independent primary sources where available and explain the verification standard.”

Informational template:
“Explain [topic] for [audience]. Cover [subtopics and timeframe], compare major viewpoints, and identify what is well established versus uncertain.”

The advanced “Under the hood” section can explain routing, agents, source tiers, models, traces, and fixed internal identifiers. It must not be the first-use guide.

5. COPY ARCHITECTURE TO PREVENT FUTURE DRIFT
======================================================================

Do not continue scattering capability claims through dozens of components.

Create a typed canonical content/capability layer, for example:

- frontend/src/content/productGlossary.ts
- frontend/src/content/researchMethods.ts
- frontend/src/content/planHelp.ts
- frontend/src/content/billingHelp.ts
- frontend/src/content/dataToolsHelp.ts
- frontend/src/content/errorMessages.ts

Use shared copy across landing, FAQ, Guide, onboarding, tooltips, and empty states where the factual statement is the same.

Separate:

- stable product definitions;
- plan/tier facts fetched from backend configuration;
- runtime availability/status;
- marketing headlines;
- technical/admin remediation.

Do not hard-code dynamic prices, quotas, pack sizes, active periods, provider availability, or feature status in multiple frontend files. Prefer backend-delivered catalog/config values and format them through shared components.

Introduce an audience property for help content:

- user
- advanced
- admin

Never render admin remediation to a normal user.

6. ACCESSIBILITY AND PLAIN-LANGUAGE REQUIREMENTS
======================================================================

- Target approximately grade 8 reading level for core user flows.
- Define a product-specific term at first use.
- Use sentence case for labels.
- Prefer verbs that describe outcomes.
- Do not use acronyms without expansion.
- Do not use color alone to indicate evidence strength, run status, or billing state.
- All disclosures, help icons, tabs, countdowns, errors, and progress changes must be keyboard and screen-reader accessible.
- Critical instructions must be visible, not tooltip-only.
- Error copy must identify what happened, what was preserved, and what the user can do.
- Buttons must say what will happen; avoid ambiguous “Continue,” “Manage,” “Submit,” and icon-only actions where consequences matter.
- Mobile layouts must retain explanations and cost/privacy warnings rather than hiding them.
- No emojis in instructional or error copy unless the established design system explicitly requires them.

9. DEFINITION OF DONE
======================================================================

This work is complete only when:

- A new user can understand the product without knowing research-method jargon.
- A user can submit a purely informational request without being told to invent a falsifiable hypothesis.
- A user can submit a story/claim-verification request and see a clear verification method.
- EZ mode explains the outcome and hides orchestration internals by default.
- Research Lab retains advanced control with definitions.
- The research plan clearly separates user requirements, system assumptions, concrete exclusions, sources, deliverables, and expected cost.
- All important buttons state their consequence.
- The user can tell the difference among subscription quota, wallet funds, and monitor tokens.
- No customer-facing page exposes server commands, secret-key examples, environment variables, or redeployment instructions.
- Dossiers, reports, revisions, and spinoffs have distinct definitions.
- Corpus, Ingest, Atlas, Embedding Viz, and Knowledge Graph each explain when to use them, prerequisites, privacy implications, and next steps.
- Public landing, Methodology, FAQ, Pricing, Guide, and in-product copy describe one coherent product.
- Dynamic price/tier/status facts have one authoritative source.
- Legacy reports remain readable.
- Existing research, billing, authentication, consent, and monitoring behavior is not broken.
- Tests prevent a future return to universal-falsification or fixed-pipeline claims.
