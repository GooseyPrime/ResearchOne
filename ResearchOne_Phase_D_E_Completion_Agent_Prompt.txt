FOUNDER DECISIONS — DO NOT BLOCK FOR THESE ANSWERS

The following product/architecture decisions are now specified:

1. Specialist agents must actually execute.
   "Registered," "selected," "shown in the UI," and "has a system prompt" do not count as execution. A specialist is complete only when an applicable confirmed ResearchBrief causes a real call, its output is parsed and validated, its result is supplied to downstream reasoning/synthesis, its cost/latency is recorded, and an end-to-end test proves the output affects the report.

2. The confirmed ResearchBrief is the source of truth.
   Use primary intent, secondary intent, requested artifacts, exact counts, user constraints, epistemic posture, and confirmed assumptions. Do not reclassify the user's speech act during execution. Do not create a second intent-blind plan.

3. The UI may advertise only the executable roster.
   "Agents that will run" must be derived from the same execution plan the worker consumes. Do not combine pipeline-stage IDs with agent-role IDs. Do not show a specialist merely because it exists in a registry. If a provider or required capability is unavailable and the specialist will be skipped, the preview must say that plainly or omit it before confirmation.

4. Use existing source-provider infrastructure before adding vendors.
   The repository already contains general web, Brave, Tavily, arXiv, Crossref, OpenAlex, PubMed Central, ClinicalTrials.gov, Scite, USPTO, and direct URL fetch providers. Build a source-connector registry and route these by intent and source class. Do not block Phase D on procuring a new paid API. New vendor integrations may be proposed only after a tested gap is demonstrated.

5. Quantitative work must use deterministic computation for arithmetic.
   Models may decide what to calculate and explain the result, but they must not be the sole calculator. Add a bounded deterministic calculation layer for supported operations. Never use eval, arbitrary user code, or an unrestricted code-execution sandbox.

6. Quantitative outputs must carry provenance.
   Every material number must retain source/chunk or input-field references, units, transformation/formula, assumptions, and uncertainty or limitations. The Data Quality Auditor must be able to reproduce or reject the calculation.

7. Specialist failures are fail-soft but visible.
   A failed specialist must not silently disappear or fabricate an empty success. Record status as succeeded, skipped, unavailable, invalid_output, or failed; preserve the reason; continue when the report can still be responsibly produced; and surface degraded coverage to the report contract/verifier.

8. Cost and latency remain bounded.
   Run independent specialists in parallel where the capability registry permits it. Enforce per-agent timeouts, output limits, and run-level budgets. Reuse the existing callRoleModel and cost-sidecar instrumentation rather than creating a second LLM-call pathway.

9. No universal falsification regression.
   Informational, descriptive, comparative, implementation, and opportunity requests must not be forced into proof/disproof framing. Story verification and adjudication may use explicit verdict/confidence structures when appropriate.

10. Phase E begins only after Phase D is genuinely executable.
    Scaffold-only tests do not satisfy Phase D.

KNOWN DEFECTS TO RESOLVE BEFORE CALLING PHASE D COMPLETE

A. orchestrationRuntime.ts currently mixes canonical pipeline-stage names with agent IDs in agentsWillRun. This creates near-duplicates such as planning/planner and can claim that agents run when they do not.

B. generatePlan() attaches researchBrief after parsePlanGeneratorJson() has already performed canonical enrichment. As a result, secondaryIntent may be missing during agent selection. The no-OpenRouter fallback path has the same ordering problem.

C. selectAgentsForBrief() always returns five nominal core agents even when the canonical intent profile skips one of the corresponding execution stages. The executable roster must come from one canonical execution-plan representation.

D. No callRoleModel invocation currently executes market_scout, competitor_mapper, demand_signal_analyst, feasibility_architect, story_verifier, or timeline_reconstructor.

E. AnimatedPipelineHero has adaptive specialist nodes, but the production PersonaAwareHero still uses PipelineSchematic. Direct component tests do not prove the adaptive hero is reachable.

F. agentsRan is currently based on orchProfile.agentsToRun, so it cannot honestly report specialist execution.

G. "All roles threaded through configuration" in PR #178 is not equivalent to end-to-end wiring. Correct documentation that implies otherwise.

PR D1 — CANONICAL EXECUTION PLAN AND SPECIALIST RUNNER

- sourceConnectors/sourceClasses selected
- execution groups/dependencies
- skip reasons
- expected output contract/template
- plan version

Use distinct types for PipelineStage and AgentRole. Never store both as ambiguous strings in one array.

For backward compatibility, accept legacy plans and derive the new execution plan at resume time. Persist the canonical plan when possible. Do not break already parked plan-gate runs.

2. Fix ResearchBrief ordering.

Attach ResearchBrief before canonical execution-plan derivation, in:

- the normal LLM plan path;
- the no-credential fallback path;
- persisted-plan coercion/resume;
- plan refinement if it can change intent, secondary intent, artifacts, or constraints.

Add a regression test:

Primary intent = comparative
Secondary intent = feasibility

The resulting execution plan must include the specialists triggered by both intents, including feasibility_architect, without duplicates.

3. Make one function authoritative.

Replace separate UI selection and runtime selection logic with one canonical builder, for example:

buildExecutionPlan(confirmedResearchBrief, canonicalProfile, runtimeAvailability)

Both the confirmation preview and worker must consume the same persisted result. The frontend may receive a display-safe descriptor generated from this plan, but it must not independently reimplement selection rules.

4. Implement a specialist runner.

Create a bounded service, for example specialistExecutionService.ts, that:

- accepts the confirmed ResearchBrief, canonical execution plan, evidenceContext, plan, query, model runtime options, BYOK override, and progress/checkpoint callbacks;
- calls callRoleModel for selected specialist roles;
- validates JSON into the typed output contract;
- retries/falls back only through existing model policy;
- records modelLog/cost telemetry through the existing callRoleModel path;
- saves checkpoints with stable keys;
- returns a structured SpecialistExecutionBundle with status per selected agent;

Suggested dependency groups:

Group 2:

Add a bounded, clearly delimited SPECIALIST_FINDINGS block to:

- general reasoner input;

PR D2 — QUANTITATIVE ANALYST AND DATA QUALITY AUDITOR

1. Extend intent taxonomy.

Add explicit intents:

- data_analysis
- forecast

Update every exhaustive intent map, parser allowlist, orchestration profile, template, classifier prompt, verifier rubric, frontend display descriptor, and regression test. A grep for all IntentId switches/maps must show no silent fallback.

Do not route every request containing a number to data_analysis.

2. Add specialist capabilities.

Add:

quantitative_analyst
- Trigger for data_analysis and forecast.
- Also eligible for comparative, opportunity_discovery, feasibility, literature_review, and recommendation only when requested artifacts/constraints call for numerical comparison, calculations, a table, sizing, rates, trends, or projections.

data_quality_auditor
- Trigger when the output relies on multiple datasets, conflicting numeric claims, extracted tables, projections, or exact numerical deliverables.
- May run after quantitative_analyst because it audits inputs and computations.

Do not select these solely from intent strings. Extend capability selection to support artifact/capability predicates from the full ResearchBrief.

3. Define strict structured outputs.

QuantitativeAnalystOutput must include at least:

- metrics/results
- units
- input values with source/chunk references
- formulas/operations
- deterministic calculation result
- assumptions
- uncertainty/limitations
- missing data

DataQualityAuditOutput must include at least:

- pass/warn/fail
- reproducibility status
- input/source problems
- unit/denominator/time-window mismatches
- calculation discrepancies
- sensitivity concerns
- corrections
- confidence

4. Add a deterministic calculation service.

Support a bounded initial operation set suitable for the product:

- sum, difference, product, ratio, percentage, percentage change
- mean, median, min, max
- weighted average
- simple compound annual growth rate when periods are valid
- ranking and normalized score with declared weights

Reject unsupported operations clearly. Validate finite numbers, units, denominators, date periods, and divide-by-zero. No eval and no arbitrary code.

The LLM proposes a typed calculation request; the deterministic service executes it; the agent explains the returned result. The Data Quality Auditor rechecks the calculation request/result and source provenance.

5. Quantitative report contract.

Intent templates and verifier rubrics must require:

- traceable inputs;
- consistent units and periods;
- formulas or method;
- distinction between observed, calculated, estimated, and forecast values;
- uncertainty and missing data;
- no false precision.

PR D2 ACCEPTANCE TESTS

- a numerical comparison request invokes quantitative_analyst and produces deterministically checked results.
- a forecast request labels assumptions and uncertainty and invokes data_quality_auditor.
- an ordinary factual prompt mentioning a year does not invoke quantitative specialists.
- mismatched units or periods produce an audit warning/failure.
- divide-by-zero and non-finite inputs are rejected safely.
- exact-count deliverables are still enforced by the contract auditor.
- revert checks prove selection, computation, audit, and synthesis integration.

PR D3 — SOURCE CONNECTOR REGISTRY, ROUTING, AND AVAILABILITY

- PubMed Central
- ClinicalTrials.gov
- Scite

2. Add a typed connector registry.

Each connector descriptor should include:

- id and display-safe name
- supported source classes/domains
- intents/capabilities served
- credential/config availability check
- cost class
- parallelism/rate-limit metadata
- result normalization contract
- provenance fields
- health/timeout behavior

Use the existing source-class classifier and ResearchBrief. Do not let a model directly execute arbitrary tools or URLs; the backend chooses from allowlisted connectors and applies existing URL-fetch security policy.

3. Required routing policy.

Use this initial mapping:

- General informational/investigative/story work:
  Tavily/Brave/generic cascade plus direct URL fetch for selected sources.

- Literature review and scholarly factual work:
  Crossref + OpenAlex; add arXiv for relevant preprints; PubMed Central and ClinicalTrials.gov for biomedical/clinical topics; Scite when configured for citation context.

- Patent/prior-art work:
  USPTO plus general web/direct official URLs.

- Opportunity, competitor, demand, feasibility:
  General web cascade and direct source fetching. Specialists create targeted query families such as pricing pages, product documentation, procurement notices, customer complaints, public filings, and official statistics. Do not pretend the existing web search rank is market truth.

- Quantitative/data analysis:
  Prefer primary datasets, official statistics, filings, and tables discovered through applicable providers. Preserve the dataset URL, access date, table/field identity, unit, and period.

- Reference lookup:
  Use the smallest adequate connector set.

4. Browser/tool specialization.

For Phase D, "browser specialization" means:

- specialist-specific bounded search-query generation;
- connector selection by source class;
- direct URL fetch and existing site-crawl/ingestion where appropriate;
- graceful detection of thin/JavaScript-only pages;
- auditable provenance and fetch status.

Do not introduce a headless browser dependency merely to check the Phase D box. First add a typed "render_required/unavailable" outcome for thin JS pages. A future rendered-browser connector can be proposed with security, SSRF, resource, licensing, and operational analysis if the golden suite shows material failure.

5. Availability and fallbacks.

At plan time, resolve configured connector availability. Never advertise Scite, Brave, or another credentialed provider when its configuration is absent. Fall back to available connectors and tell the plan/report what coverage is reduced.

Provider failure must:

- retain attempted connector and reason;
- try an allowed fallback when policy permits;
- avoid treating zero results as proof of absence;
- surface coverage limitations to specialists, verifier, and final report.

- unconfigured provider is not advertised and falls back cleanly.

PHASE E — EVALUATION AND OPTIMIZATION

After D1–D3 merge, implement Phase E in separate PRs.

E1. Golden prompt suite

Build fixtures across every intent and depth combination, with extra regression cases for:

- the original online-opportunity failure prompt;
- pure informational overview;
- comparative decision;
- story verification;
- explicit true/false adjudication;
- timeline reconstruction;
- feasibility/implementation;
- literature review;
- quantitative analysis;
- forecast;
- reference lookup;
- primary intent plus materially different secondary intent;
- unavailable connector;
- specialist failure/degraded run.

Each fixture needs machine-checkable expectations:

- correct primary/secondary intent;
- required/forbidden specialists;
- required/forbidden source classes;
- required artifacts and exact counts;
- forbidden framing/sections;
- citation/provenance requirements;
- maximum allowed premise-questioning for non-adjudicative work;
- cost/latency budget;
- contract-audit outcome.

Use mocked providers/models for deterministic CI and a separately gated live evaluation job for real provider/model quality. Do not make ordinary PR CI depend on live paid APIs.

E2. A/B framework

Do not deploy uncontrolled copy changes. Define versioned variants for:

- clarification-question strategy;
- plan-preview wording;
- report template/outline.

Measure:

- plan confirmation without edits;
- clarification completion/abandonment;
- contract-audit pass rate;
- user revision requests;
- report completion;
- cost and latency;
- qualitative rating where available.

Protect privacy and avoid logging raw sensitive prompts unnecessarily. Feature-flag variants and retain a deterministic assignment key.

E3. Routing optimization

Tune only from golden-suite results and production telemetry. Optimization order:

1. contract correctness and citation support;
2. intent/deliverable fidelity;
3. coverage;
4. latency;
5. cost.

Never reduce cost by silently omitting a specialist required for the confirmed contract. Prefer conditional selection, parallelism, smaller adequate models, bounded context, and connector minimization.

E4. Fine-tuning decision

Do not fine-tune during initial Phase E. First collect enough labeled examples of:

- corrected intent/secondary intent;
- plan edits;
- agent-routing corrections;
- contract-audit failures;
- accepted/rejected outputs.

Create a decision memo with dataset size/quality, privacy/licensing, baseline versus tuned evaluation, deployment cost, rollback, and drift monitoring. Fine-tune only if prompt/rule-based routing remains a demonstrated bottleneck.
