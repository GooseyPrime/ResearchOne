## How to work on this repo

The mechanics are awkward and cost a previous session an hour. Read this part.

**Where the code is.** `C:\Users\brand\Projects\ResearchOne` on Brandon's
Windows machine (`goosey-yoga`). The Cowork VM mounts it at
`$HOME/mnt/Projects/ResearchOne`.

**Pushing only works from Windows.** Three environments, three different
network situations:

| Environment | Tool | GitHub |
|---|---|---|
| Cloud container | `Bash` | Read only. Clone and fetch work; **push is refused** by the git proxy ("not in this session's authorized repository set"). |
| Cowork VM | `device_bash` | **No GitHub at all** — the proxy returns 403 on CONNECT. |
| Windows itself | `Windows-MCP__PowerShell` | Full access. `git push` and `gh` work here. |

So the working loop is:

1. Clone into the cloud container and do all editing and testing there — it is
   the only place with a fast filesystem and a 600s command timeout.
2. `git format-patch origin/main..HEAD --stdout > /tmp/x.patch`
3. `SendUserFile` the patch, then `device_commit_files` it into the repo root.
4. From PowerShell: `git am .x.patch`, delete the patch, `git push`.

**Do not run `git am` through `device_bash`.** Its 45-second ceiling kills it
mid-apply and leaves `.git/index.lock`, `packed-refs.lock` and
`REBASE_HEAD.lock` behind; recovering costs several rounds. `device_bash` is
fine for reading and for `ls`.

**The Windows bridge times out.** `Windows-MCP__PowerShell` has a hard 60s cap
regardless of the `timeout` argument, and it drops out for minutes at a time.
Keep commands short. If it is unreachable, do the work in the cloud container
and hold the patch until it comes back.

**Setup in the cloud container:** `npm ci` in `backend/` and in `frontend/`
(about 90 seconds each, run them in parallel). Gates:

```bash
cd backend  && npx tsc --noEmit -p tsconfig.json && npx vitest run && npm run lint
cd frontend && npx tsc --noEmit -p tsconfig.json && npx vitest run && npm run lint
bash scripts/ci/assert-tier-a-no-banned-jargon.sh    # from the repo root
```

`npm run build` in `frontend/` will fail without `VITE_CLERK_PUBLISHABLE_KEY`.
That is deliberate and correct; `tsc` covers you.

  full engine. This mattered more than it sounds: the weaker path used the

  gate used to pass the moment a specialist model produced a non-empty array.
  Analytical coverage and independent evidence are separate quantities now, and
  verdict intents fail closed without material the requester did not supply.

  challenge strength and evidence policy asserted in CI with no model calls.
  Writing it found four routing defects, including one where "verify whether

  HTML so their titles were their URLs.
- **"Skeptic" is gone from the product's vocabulary** — with the caveat that the

## One thing worth internalising

Brandon's complaint, in his words, was *"the reports keep getting worse and
worse with your 'improvement changes'."* He was right. Three sessions in a row
optimised the UI while the product was broken.

The work queue opens with the rule that came out of that: **report quality
outranks everything.** A run that produces a badly-numbered, table-less report
citing an unrelated paper is not improved by a nicer run page, a cleaner form,
or better vocabulary. If a session has time for exactly one thing, it is the
report.

The three P1s that review caught in this branch were all the same shape — a fix
that computed the right answer and handed it to something that ignored it, with
a test that checked the helper instead of the pipeline. Watch for that one
specifically. It looks like progress in the diff and changes nothing in
production.
